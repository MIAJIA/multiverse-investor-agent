# 改动说明：一张图多条分支 + 批准计划（方案 B）

2026-10-18 · 第 2 版（已采纳评审意见）· 状态：**待 Mia 定范围**（第 9 节）

本文是这次改动的唯一依据。PRD、工程设计、核心、前端、eval 的改动都以本文为准；本文没写的，维持现状。

## 1. 一句话

一张图里有竞争的分支，每条分支通向一个结论，每个结论配一份由系统预先填好的计划（进场条件、离场条件、关键依赖）。用户审阅、按需修改，然后批准其中一份，也可以一份都不批准。

## 2. 为什么改

从用户的角度看，决策取决于「你相信哪个前提」。

- **分叉点就是关键依赖**：几条分支在哪里分开，哪里就是最值得检验的前提，不需要另外去找。
- **条件告诉你现实在走哪条路**：同一个可观测信号，在一条分支里是进场条件，在另一条分支里往往是离场条件。例如「集成激光开始量产出货」。
- **不是投资教练**：计划由系统给出，用户只做 copilot 和 human-in-the-loop：审阅、修改、批准。批准是必须的，因为执行需要人点头。不要求用户写誓言式的自由文本。

## 3. 决定清单

| # | 决定 | 取代了什么 |
| --- | --- | --- |
| D-B1 | 在选中的那个方向内部，Inspect 在真正存在争议的地方给出 2–3 条竞争分支，每条通向一个 terminal。没有真正的争议时，1 条也合法，不为凑数造分支。Discover 的候选方向不变，分支只在用户选中的方向内展开 | 单一路径 |
| D-B2 | 每个 terminal 必须有一份计划，而且只有一份。每份计划都有方向和标的。「不交易」= 一份计划都不批准，不另设没有方向的计划 | 一个版本只有一份提案 |
| D-B3 | B2 从「签字」改成「批准计划」：计划预先填好；选一条分支；没有依据的阈值高亮「需要你确认」；点批准；备注可选。原来三个必填的自由文本框去掉 | 签字表单 |
| D-B4 | 一个版本里最多只有一份计划处于已批准状态，批准一份会撤销同版本其他计划的批准。几条分支并列受益时，也不能组合批准（下一期再考虑） | — |
| D-B5 | 改假设 = 更新这张图：只重算下游，生成新版本，可以撤销。**只有受影响的计划会失效**，需要重新批准；其他计划的批准保留（判定规则见 4.3） | 「基线 / 情景」并排对比作为主流程 |
| D-B6 | 前提确认沿用逐条勾选：没勾选的前提，依赖它的结论在界面上变淡，不调用模型 | 删除节点和连线（不做） |
| D-B7 | 模型对原话的改写仍要用户确认，在计划顶部用一行「我们把你的想法理解为……✓」完成 | 签字表单里的「可检验判断」 |
| D-B8 | 情景叠加（已实现）和多情景对比页（已实现）保留，但退出主流程：后端照常工作，前端的 #scenarios 页标为「实验」 | 多情景列表进入主流程（不做） |
| D-B9 | **假设性的分支和有资料支持的分支，在界面上要截然不同，用户一眼就能分辨。** 分支类别由代码推导，不由模型标注（见 4.2） | — |

**明确不做**：删除节点和连线；AddShock 交给模型、用户自己加分支（即方案 C）；更新 / 情景两种模式的切换；没有方向的计划。

## 4. 核心（后端）改动

### 4.1 数据结构（`catalyst/schema.py`）

- `ProposalDraft` 和 `TradeProposal` 加 `terminal_id`。`Direction` **保持必填**。
- Inspect 第二步的输出（`InspectPlanOutput`）从 `proposal` 改成 `proposals: list[ProposalDraft]`。评审在内存里模拟过这份新 schema：union 有 13 个（上限 16），没有超限。
- 每个版本存一组提案。API 版本包**一次切换**成 `proposals: list`，不保留过渡字段 `proposal`，免得「默认显示哪一份」变成由模型的输出顺序决定。`store.get_proposal` 读到旧文件（单个 dict）时，包成只有一项的列表。
- `ProposalMeta.proposal_version` 改成 `f"{g.version}.{terminal_id}"`，避免同一版本里的多份计划重名。

### 4.2 分支推导（新文件 `catalyst/branches.py`，纯函数，代码裁决）

`store.bundle`、`promote`、`web/scripts/make_fixtures.py` 都调用同一个函数，版本包里新增：

```
branches: [{terminal_id, divergence_node_ids, own_node_ids, own_edge_ids, kind, trunk}]
```

- **独有部分**：`own_node_ids = (ancestors(t) ∪ {t}) − ⋃ ancestors(其他 terminal)`；`own_edge_ids` 是终点落在 `own_node_ids` 里的边。这样不会漏掉旁路的根节点。
- **分叉点**：一个节点的几条出边各自能到达的 terminal 集合不一样，这个节点就是分叉点。
- **kind**，按优先级取三类之一：
  1. `hypothetical`（假设）：这条分支的**全部祖先**（含共用上游）里，有任何一个是：
     - role=shock 的节点；
     - 情景冲击新增的节点；
     - 用户改过的假设（本版本及祖先版本 `scenario.ops` 的 target）。

     注意：用户改过的假设会让所有依赖它的分支都变成 hypothetical。
  2. `evidenced`（有资料支持）：独有部分的**每一条边**都不是 model_only，且都带 supports 证据；独有节点里没有 contradicted；用到的资料包不是合成的。
  3. `model_only`（仅模型推断）：其余情况。合成资料包支撑的分支也降级到这一类，并标注「资料为占位」。
- **trunk**：共用上游的强度，取值 evidenced / model_only，计算方法同上。避免主干全是推断时，分支本身却显示成实线。
- **残余风险**（存疑）：「尚未发生的事件」依赖模型标成 role=shock，模型可能漏标。提示词里写死这条要求；人工复核表加一项。

### 4.3 改假设后，哪些计划失效（D-B5）

一份计划只要满足下面任一条，就算受影响：`confirmed` 重置为 false，`confirmed_claim_ids` 剔除写范围内的 claim：

1. 它的 terminal 在这次分叉的写范围里。写范围是改动目标的全部后代，所以挂在共用上游或分叉点上的影响都会被这一条抓到。
2. 它的进场条件或离场条件挂在写范围里的 claim 上。这一条覆盖了「镜像条件挂在对手分支上」的情况。
3. 它的 key_dependency 指向写范围里的 claim 或条件。

不满足任何一条的计划，批准原样保留。判定只看代码算出的写范围，不看模型的 assessment。

**已知盲区**（存疑）：竞争关系不在图结构里。如果改的是对手分支独有的前提，而本计划没有引用它的任何条件，本计划不会失效。B3 对此给一句提示：「对手分支变了，你的计划没有直接受影响，但值得再看一眼」。

这一条反转了现有行为：`tests/core/test_api.py` 第 56 行断言「签字不会在分叉时丢失」，要同步修改。

### 4.4 校验

- 计划的 terminal 集合必须**恰好等于**图上全部 terminal（阻断）：每个 terminal 一份，不多不少。
- `direction.instrument` 必须属于该 terminal 的 instruments。
- 计划引用的条件，它所在的 claim 应该是该 terminal 的祖先，否则给非阻断提示。条件可以被多份计划共用。
- `_support_status` 除了进场条件和 key_dependency 所在的 claim，还要纳入这条分支独有的 claim，仍由代码计算。

### 4.5 流程

- `sign` 的语义改为「批准」，接口名暂不改：
  - `clarified_statement`、`criteria`、`deadline` 改为可选，默认沿用计划里的值。`api.sign_run` 目前直接读 `body["clarified_statement"]`，缺了会报 KeyError，要一并修。
  - 新增必填参数 `terminal_id`。
  - 在产出的新版本里，只有被批准的那一份是 confirmed（D-B4）。
  - `condition_overrides` 保留：改阈值或日期不调用模型，代码重新判定。
- fork：`proposal` 参数改成 `proposals`，派生时逐份重算；按 4.3 只重置受影响的计划。

### 4.6 提示词（提升 `PROMPT_VERSION`）

- **图那一步**：在真正的争议点给出竞争分支，分支之间共用上游，不为凑数造分支。**尚未发生的事件一律写 role=shock**（删掉原来「或明确写成假设」的说法）。把提示词里「一个标的」「一份提案」的措辞改掉。
- **计划那一步**：每个 terminal 一份计划，鼓励互为镜像的条件。
- 提升版本号以后，现有录音全部失效（`eval/out/haiku-realpacks`、`runs/D1` 等），**需要实时调用模型重新录制**，成本和时间已计入第 9 节。

## 6. eval 改动

- **防止静默通过**：runner 里有用 `get(out, "proposal") is None` 判断的地方（`runner.py` 第 192、214 行）。字段改名后这些判断会恒为真，必须改成显式读 `proposals`；字段缺失时直接报错，不能当成「没有提案」。
- **gate 的聚合规则**：案例里的 `"gate": "WAIT"` 解释为**每一份计划**的 gate 都必须等于这个值。
- **其他检查**也改成逐份计划检查：null 阈值必须带说明、改写过的原话需要用户确认。
- **C1 的 golden 图**有 3 个 terminal（LITE、TSM、MRVL），它们是**并列受益，不是相互竞争**。图本身不用改，但 `make_fixtures.py` 里手写的提案草稿要改成 3 份。C3 走的是分叉机制，期望不用改。
- **人工复核表**新增两项：分支是不是真正的竞争，而不是为凑数编出来的；尚未发生的事件有没有标成 shock。**不新增**「D1 必须出现某条分支」这类自动检查，免得 eval 反过来塑造提示词。
- `INTERFACE.md`、`fakes.py` 同步更新。
