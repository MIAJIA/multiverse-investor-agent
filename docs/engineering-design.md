## Design goals and three principles

Architecture in one sentence: turn an event into a small number of trade arguments worth researching, make clear what each argument depends on, and let the user see how the judgment should be updated after one key assumption changes — delivering the end-to-end experience with structured generation, deterministic validation, versioned state, one local fork, and a targeted eval. This version is the one after the two audit rounds of 2026-10-18: probability propagation, unsourced disagreement scores, and infrastructure commitments beyond three hours were removed; the final audit's 4 P0s (entry-condition logic, condition time semantics, fork write scope, evidence before reasoning) and 3 P1s have been merged into the body.

Three principles. Every later design decision can be traced back to one of them:

1.  **The model proposes, the code decides.** The LLM produces the graph's structure, mechanisms, invalidation conditions and explanations; the code owns the schema, the invariants, merging, diffs and the ledger. Any judgment that a next-generation model will do better does not go into code; any rule that does not change as the model gets stronger (no cycles, invalidation conditions non-empty, a fork changes only inside the write scope) goes only into code.

2.  **Everything is versioned, and everything can be replayed.** The belief, the graph, the proposal, the fork and the evaluation results are all immutable snapshots (Immutable Graph Snapshots). Each operation is recorded in the Operation Log with its origin (model / code / user, prompt version, tool calls). Audit, diff and eval are only reads of the snapshots and the operation log.

3.  **Seams before features.** But leave only two seams: the Reasoner (who does the reasoning) and the Evidence Provider (where evidence comes from). The core layer does not know their implementations. Things whose semantics are not settled — propagation, pricing, scoring, evaluation — get no interface, and are abstracted once the semantics are stable. The procedure for swapping a model or an evidence source is: swap the implementation, run the same eval, and look at the per-case results — and not read the code.

One sentence for the implementer (from the engineering audit): **the model is responsible for proposing causal hypotheses and revision suggestions, and the system is responsible for maintaining state, enforcing boundaries and showing uncertainty. Correct structure does not mean a correct causal judgment.** The validators guarantee that fields are complete, there are no cycles, and a fork does not go out of bounds; whether a causal chain stands is answered by the evidence status and human review, and not by any formula. A principle that can be said in an interview: We separate what the model believes, what the evidence supports, and what the system is allowed to change — constrained reasoning, grounded judgment, auditable state changes.

Assumption: a Python service + a thin front end (a read-only React Flow canvas, with all write actions translated into back-end operations; see "Catalyst — Front-end design" for details); the model is called through an API. The language is not part of the architecture.

## Architecture overview



Layered architecture · edge, core, policy

The edge layer only translates and renders. The core layer owns the schema, validators, version snapshots, diff and eval, and treats the two boundaries alike. The boundary layer is the Reasoner and the Evidence Provider, and swapping a model or an evidence source later touches only this. The model is called only by the core layer's generation flow, and can write the graph only through the validators.

## Core data model: ClaimGraph and TradeSpec

Two first-class objects: the ClaimGraph (the causal graph, the object of audit and fork; it is a DAG and not a chain — one node can influence several outcomes, several paths can converge on one outcome, when one path fails the other paths remain, and one external shock can influence several nodes; in three hours only the one selected trade path is analysed in depth, but the data structure does not assume linearity) and the TradeProposal (the conditional trade proposal, the deliverable). The proposal is derived from the graph and is not an independent input. The most important change after the audit is to **separate the Claim (what happened, what is assumed) from the Condition (which concrete observation decides that it holds or has failed)**. Not every causal node can correspond to a numeric series. Whether a policy has taken effect, an export control has been announced, or a military event has happened is decided by a formal document or a verified event record, and forcing a numeric four-tuple onto it only pushes the model to invent indicators.

State has four layers, each its own field and not shared. **Scenario** records what the current world line assumes (which assumptions were changed, which shocks were added), and carries a thin Assessment: claim_id → unaffected / challenged / unresolved, which expresses which paths are affected under the current scenario — when the user changes an assumption it writes only here, and does not change an existing Claim's evidence_status from supported to contradicted. **Claim.evidence_status** records whether the statement is supported, contradicted or unknown (contradicted is advanced by a contradicts excerpt that is cited and not rebutted, and not by the scenario). **Condition.verification_status** records whether there is a workable way to verify, and **Condition.evaluation_status** records whether the condition is met, not met or cannot be told. **Proposal.support_status** records whether the trade argument is still supported by the current evidence. "Iran is struck the next day" is an assumption in a scenario, and in reality it can be an event confirmed by evidence; whether it invalidates the assumption "safe passage" is a Condition's evaluation, and not a Claim's state. The default WAIT is because evidence that satisfies the conditions has not yet been obtained, and it does not claim to have observed that a condition is not met.

| Object | Fields | Who writes | What the code can validate | What the code cannot validate |
|-----------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------|
| Scenario | version, base_version, root_version (a stacked scenario points to the original baseline), ops (accumulated when stacking): \[{kind: change_assumption / add_shock, target, value}\], assessment: {claim_id: unaffected / challenged / unresolved} | Code records the user's operations | The baseline version exists and has not been overwritten | — |
| Claim | id, statement, original_statement (the user's own words and original time before normalisation), evidence_status (supported / contradicted / unknown), time_bucket, instruments (only on terminals) | The model writes the statement; the status is advanced by evidence | Fields complete, the user's own words kept, a terminal resolves to a whitelisted instrument | Whether the statement is true, whether the causation holds |
| Condition | claim_id, kind (numeric / document / event), predicate (observed_by / not_observed_by / at_deadline), series or source, comparator, threshold (when unknown, a type-correct null + threshold_note, and "TBD" is not stuffed into a numeric field), anchor (time starting point: an absolute date, or the scenario event it depends on), deadline (the time of final evaluation), observation_window (the time interval that should be checked), rule, verification_status (verifiable / unverified), evaluation_status (met / not_met / unknown) | The model proposes; evaluation is by rule | The predicate is within the enum, anchor and deadline are non-empty and deadline is not earlier than anchor, kind matches the source type; a null threshold is legal but must carry a note; verifiable ≠ met is written as a code rule; not_observed_by can give met only when the observation_window has ended, the source covers that window and nothing was observed in the window (deadline passed with nothing happening = the condition holds), observed in the window gives not_met, and everything else is unknown | Whether the threshold has a basis, whether the series really exists, whether the source supports this conclusion |
| Mechanism (edge) | from, to, channel (enum), sign, lag_days, mechanism, evidence: \[{tier, source_id, excerpt_id, stance (supports / contradicts / neutral, must match the excerpt), supports (which part of the claim)}\] or model_only | The model | No cycles, every node is on some path to a terminal, channel is within the enum, every edge has evidence or an explicit model_only; the cited excerpt_id really exists in the current Evidence Pack (Reference Validator) | Whether the evidence really supports this edge |
| Graph version | version, parent_version, op, nodes, edges, model_output_ref, observations_ref | Code | The hashes of nodes and edges outside the write scope do not change | — |

**TradeProposal = derived analysis + user judgment + graph version number**, **exactly one per terminal** (`terminal_id`), with status draft / needs_review. The derived analysis is generated from the graph, and regenerating the graph does not overwrite the user's own judgment. What the user approves is a plan, not a trade execution, and at most one plan per version is approved. Fields: terminal_id, approval_reset / rival_changed (written by code after a fork: approval was revoked / another plan in the same version was affected), critic (disabled in this phase), direction (instrument, direction, term), entry_conditions, exit_conditions (lists of Condition objects), key_dependency (the key dependency most worth checking first on the currently selected path + why it was chosen; unknown when there is not enough basis, and not forced; its failure does not automatically invalidate the whole argument), user_judgment (the original statement + the confirmed judgment + the deciding conditions + the deadline + a note; this one sentence must be the same across the plans in one version; confirmed, confirmed_claim_ids and probability can be written only by the user, and the model output schema does not have these fields), market_reference (shown if available, stating which question it answers, otherwise no_market), scenario_ref (challenged premises + what to check next + baseline version number), support_status, audit (graph_version, the chain, the evidence), meta (proposal_version, prompt_version, model, approval_required = true). There is no position-size field. When Discover returns zero candidates, no proposal is generated, and an instrument is not made up just to produce a proposal.

"WAIT" is still the default state, and the decision rule is written as code and not as prose. entry_conditions are AND by default — a condition passes only when every one has evaluation_status met; any one unknown → WAIT; any one not_met → BLOCKED; a missing condition or insufficient data does not count as met; an empty entry_conditions does not pass automatically because of the logic of the empty set, and is likewise WAIT. exit_conditions trigger on "any one met" only when explicitly declared as OR. key_dependency is a reference to a Condition, and not a string that can be compared directly with unverified: check the verification_status and evaluation_status of the Condition it is tied to, and the evidence_status of the corresponding Claim. Even when all are met it only enters Ready for Review (needs_review), and there is no Ready to Execute. The wording is still "evidence that satisfies the conditions has not yet been obtained". Truth table:

| entry A | entry B | Decision                                                         |
|---------|---------|------------------------------------------------------------------|
| met     | met     | Pass → Ready for Review (not Ready to Execute)                   |
| met     | unknown | WAIT                                                             |
| met     | not_met | BLOCKED                                                          |
| unknown | unknown | WAIT                                                             |
| empty set | —     | WAIT (the empty set does not pass automatically)                 |

Versions: the unified term is **Immutable Graph Snapshots + Operation Log**. In three hours only the chain of snapshots graph v1 → operation → graph v2 → diff is needed, together with the input, model output, tool observations and prompt version. The baseline world line is kept as the original version, and a scenario produces a new version and does not overwrite it. It is enough to be able to replay recorded results, and we do not promise that calling the model again gives the same result. Full event sourcing, schema migration and multi-user isolation go into Future Work.

## Runtime flow



Runtime state machine · generate, fork, slow loop


Two lanes, and one deferred. Generate: belief (A + optional B) → Claim and Condition → Evidence Pack loaded into the context → graph v1 (Discover gives 0–3 candidates, or Inspect A → B, with edges citing excerpts from the evidence pack) → citation validation + structural validation → proposal v1 (draft; WAIT when the entry conditions are not all met or the key dependency is not verified). Fork: ChangeAssumption or AddShock → the code first fixes the write scope → the model changes only the nodes and edges inside the scope → the code computes the diff, writes the challenged paths into the Scenario Assessment, and everything else stays character for character the same → one plan v2 per terminal, where the approved plans the write scope touches become invalid and the rest are kept. Approve: the user confirms "We understood your idea as …", edits thresholds or dates as needed, approves one plan (or none), and a new version is produced without calling the model. The slow loop (evaluation at expiry, calibration, failures entering the eval) is deferred as a whole. Each arrow produces a new version snapshot, and nothing is modified in place.

## Agent loop and harness

One controlled generation path, **in three logical stages, with model calls made on demand and not a fixed three:** Discover (0–3 candidate cards, with only a short rationale, no full chain built), Inspect (after the user picks one, or when B is given directly, build the causal chain and conditions for the selected one), Fork (counterfactual reasoning, patch, diff), plus one optional critic call. Discover and Inspect can be merged: when the first output is already complete enough for the selected direction, the second call is not made; Fork is handled separately. In the implementation Inspect is split into two structured calls (build the graph, produce the plans). With web search on, the research loop runs before Inspect, and after the graph is built the code finds the gaps, runs at most one follow-up round, and reruns from scratch (see the revisions at the start of this document). For AddShock in three hours, predefined demo shock attachment points are used, and Stage 1 is done by the code with a table lookup, with no extra model call; for an arbitrary external shock Stage 1 has one more call — the README states this is a current demo limitation. The document constrains each stage's input, output and cost cap (max_model_calls_per_stage), and does not promise a fixed number of calls; the actual number of requests is also affected by evidence retrieval and by retries after validation failures. A + B skips Discover. The retry cap is 2, and beyond it a structured failure is output. The two paths share the same graph schema, the same validators and the same data contract — the UI, the agent and the eval do not each define their own.

| Step | Who does it | What it does |
|---------------------------|----------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Normalisation | Model | Rewrite the belief as Claim + Condition; keep the original time and event definition ("opens next week" ≠ "passage restored by 30 November"), and after rewriting have the user confirm which one they are signing; mark what cannot be decided as unverified; if the threshold is not known leave null and write a note, and do not invent an indicator; a relative time ("within 72 hours after the opening") must state its anchor — in three hours only absolute deadlines are supported, or the relative time is computed after the user specifies the scenario starting point, and the model is not allowed to fill in a plausible-looking date itself |
| Stage 1 · Discover (no B) | Model | At most 3 candidates or an explicit abstention (0 is legal); each candidate is marked by its evidence as one of three kinds: a grounded research candidate / a research hypothesis to be verified / not recommended to continue; the ranking is research priority, and on timeout it falls back to unranked candidates instead of deleting Discover |
| Stage 2 · Inspect | Model | For the selected direction or the given A → B, give a causal path sufficient to explain the conclusion (a DAG subgraph allowing branching and converging, with depth set by the question), the mechanism and Condition for each edge, or no_chain + a reason; the display layer folds by default to ≤3 main stages (max_visible_hops), and key additional dependencies (such as the airline having hedged fuel) are listed in the details — folding is a way of displaying, and the model is not allowed to omit reasoning |
| Grounding | The Evidence Provider supplies the material first, the model cites it, the code validates the citations | The order is evidence before reasoning: knowledge-base excerpts (retrieved by pack, each with source_id, excerpt_id, source, date, original text, stance) enter the Reasoner's context first; the local knowledge base goes into the context whole; with web search on, the research loop searches the whitelisted sites, at most 5 searches and 5 fetches per round, and after the graph is built the code finds gaps and runs one follow-up round; all the excerpts retrieved in this round are stored whole in the version snapshot (observations_ref), so that the audit still matches if online content changes later, and the model cites specific excerpt_ids when building the chain — and does not make up a causal story first and then find material to fit it, which would degrade into citation laundering; the Reference Validator checks that every citation really exists and belongs to the current evidence pack; each piece of evidence states its stance (supports / contradicts) and which part of the claim it concerns; the evidence pack of every demo case contains at least one piece of opposing material, and the model must respond to a contradicts excerpt — either mark that Claim contradicted, or explain why it is not a contradiction (the idea comes from LinqAlpha's Devil’s Advocate); if it cannot be obtained, mark it explicitly model_only, and it must not be marked as backed by evidence; choose the evaluation method by Claim type. Whether the quoted original text really supports the mechanism is checked by hand in E1 |
| Validation | Code | Decides structure only: schema, no cycles, predicate enum, citation exists, write scope (nodes and edges); it does not decide depth — depth is set by the question, and only the display layer folds to 3 main stages by default; failing that, the specific errors are sent back to the model to rewrite that part |
| Key dependency | The model proposes, a person can change it | The model first proposes the key dependency that has the most decision impact on the selected path and explains why, and then considers observability; if the basis is insufficient, mark it unknown and do not force a choice |
| Stage 3 · Fork | Code + model | The write scope is fixed by the code before the graph is changed, and is not authorised by the same model output itself. ChangeAssumption: write scope = the changed target itself + the downstream nodes and edges that depend on it, computed by the code from the baseline graph. AddShock two-stage contract — Stage 1 Impact Identification: the model only proposes which existing nodes the new shock affects and which edges need to be added; the code checks structural legality and fixes the write scope accordingly. Stage 2 Scoped Re-evaluation: the model submits a Patch according to the write scope already fixed; any change to nodes, edges and related Conditions outside the scope is rejected. Read scope = the whole graph context. The baseline version is kept, and the scenario is written into a new version. Challenged premises are written in the Scenario Assessment (claim_id → unaffected / challenged / unresolved), and do not change a Claim's evidence_status. Number of calls: the three-hour POC predefines the demo shock's attachment points, Stage 1 is done by the code with a table lookup, and Fork calls the model once; one model call each for Stage 1 of arbitrary external shocks is left for later. A shock may affect several nodes, and the multiple paths are assessed separately: one path being challenged does not mean the final argument has failed, and other paths that still hold are kept as usual. The code can only guarantee that the scope complies; whether the impact location is right in financial causation remains the semantic review of E1 / E2. |
| Proposal | Model + code | Generate one draft plan per terminal; the code validates that the terminal set matches exactly, the instrument belongs to that terminal, the Condition objects are complete, and the change can be traced to some modified or added assumption; approval is done by the user in B2 |
| Critic (disabled in this phase) | In future the model (another prompt) | Checks only the one chain the user selected: whether the key dependency was chosen right, and whether there is sycophancy or excess skepticism; in this phase it returns "Not enabled: out of scope for this phase" and does not call the model |

The tools are read-only, and appear only in the research loop: server-side `web_search` / `web_fetch` (`allowed_domains` = the 19 whitelisted sites, and the code checks each URL again; for excerpts only the citation's original text is taken). The local knowledge base has no retrieval tool and goes into the context whole (the BM25 `search()` is written and is left for a later switch to RAG); `markets.lookup` is not implemented, and always returns no_market. The reasoning-stage requests contain no tools at all. The graph can be written only through `graph.commit(version)`, which is the validator's only entry.

Two hard rules: the model may read the whole graph and may write only the nodes it is allowed to, and out-of-bounds writes are discarded; output that fails validation does not enter a version snapshot and goes only into the trace. What was deleted must be stated: there is no p_model, no confidence on each edge, no cumulative probability, no min_chain_prob, no propagation formula — a fork answers "which paths depend on the challenged premise", which is a structural question and not a probability question.

## Extensibility: keep only two abstract boundaries

The version before the audit had six plugin interfaces and two propagators. After the audit only two boundaries are kept, and the rest are ordinary functions. Reason: Scorer, Propagator and Resolver do not yet even have correct domain semantics defined, and designing a stable interface for them would harden a mistake — a wrong abstraction is harder to maintain than no abstraction for the time being.

| Boundary | Input → output | Three-hour implementation | Can later be replaced by |
|-------------------|------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------|
| Reasoner | (graph context, operation: generate / inspect / change_assumption / add_shock) → a candidate graph or a subgraph patch | One Claude call + structured output | Another model, multi-model review, expert rules |
| Evidence Provider | Evidence pack → material with source_id / excerpt_id; claim or edge → \[{tier, source_id, excerpt_id, stance, supports}\] or missing | Knowledge Base: several packs under a unified interface; each pack = one industry + an excerpt file organised from that industry's most authoritative sources (each excerpt with source_id, excerpt_id, source, date, original text, stance). In three hours there are only two packs: the Semiconductor Pack (TrendForce free articles manually organised into a few dozen excerpts; TrendForce covers only semiconductors) and the Hormuz pack (3–5 hand-written excerpts); later each industry adds a pack from its own more authoritative source, the interface unchanged, without requiring one data source to cover all industries. Online search within the whitelist is one pack under the same interface, off by default in three hours, with one case left on for demonstration; model_only must not be marked as backed by evidence | An internal research library, a market data interface, formal announcement sources |

The model is specified by one parameter of the Reasoner, and swapping the model to run the same eval needs no other mechanism. Ranking, key-assumption selection, diff and validation are all ordinary functions, and whether to abstract them is decided once the semantics are stable.

## Verifiable: Eval design

Three hours evaluate only four things. What is measured is "whether the reasoning has a basis, whether the invalidation conditions are meaningful, whether the fork stays in bounds, whether it refuses when it should, and does not refuse when it should not" — not whether the fields are complete. Only the Non-interference part of E3 can be fully automatic; E3's Expected Impact relies on a small number of golden cases whose expectations are specified by hand; E1, E2 and E4 are reviewed by hand on a small sample, and do not rely on the schema alone or on another round of LLM judge.

| Eval | What is accepted | How it is tested | External data |
|---------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------|
| E1 Grounded reasoning | Causal links are consistent with the material provided; unknowns are marked unverified / model_only, and no indicator or threshold is invented; contradicting excerpts in the evidence pack are seen and answered | Check edge by edge by hand against the material; "the key excerpt was not retrieved" and "retrieved but reasoned wrongly" are reported separately, with an extra retrieval-hit column per case | CausalT5k (YES cases); FinCausal passages can serve as "the material provided" |
| E2 Meaningful invalidation conditions | The Condition is concrete and decidable, and has a real logical connection with the core argument; negative conditions are legal, vague statements are not; a null threshold (with a note) is legal; verifiable does not equal met | Human review: if this condition were replaced, would the argument still stand | None, must be self-built |
| E3 Fork integrity | Two parts. Non-interference: after ChangeAssumption and AddShock, the nodes and edges outside the write scope (including mechanisms) are character for character unchanged; AddShock adds only impact relations that were explicitly identified; the baseline version is still there. Expected Impact: in the preset golden cases, the "paths that should be challenged" specified by hand really are marked challenged, and the proposal correctly reflects this change — otherwise a system that changes nothing could also pass E3 entirely | Non-interference: a deterministic automatic test, comparing hashes of nodes and edges + change provenance; Expected Impact: for a small number of golden cases such as C3, specify the expected impact set by hand and compare automatically | None, must be self-built (CLadder can only help check the model's counterfactual logic) |
| E4 Appropriate abstention | Refuse or abstain when evidence is insufficient; a grounded candidate is not wrongly refused; do not follow a user's assertion | CausalT5k's three label classes + self-built negative controls + opposing excerpts in the evidence pack | CausalT5k |

**How CausalT5k is connected, and what its labels mean.** Go through our own Inspect entry: `scenario` is the material provided, and `claim` is split into A → B. Each case under the repository's `final_dataset/clean/` has `scenario`, `claim`, `label` (YES / NO / AMBIGUOUS), `pearl_level` (L1–L3), `trap` and `gold_rationale`; take D3 Markets & Finance. The label targets a **specific causal assertion given the material**, and is not "whether there is an A → B path in the world", so the expected behaviour is: YES → identify why the material supports the assertion; NO → explain why the assertion does not hold under the current material (the reason should hit the trap in `gold_rationale`); AMBIGUOUS → explain why the evidence is insufficient to decide. no_chain is a product output state, and does not mechanically equal NO. Among its four traps, the Skepticism Trap (should say YES but refuses) tests the second half of E4, and the sycophancy trap tests "the user asserts it and the model goes along and says YES". CausalT5k evaluates the causal judgment on a given scenario, and does not prove that the Evidence Provider found reliable sources — the latter is evaluated separately. When running the Inspect eval on CausalT5k, output only the causal judgment (label + reason), and do not force a Trade Proposal: its samples cannot necessarily be mapped to instruments on the trading whitelist, and forcing a mapping would let instrument errors contaminate the result of the causal reasoning.

**First version: 10 cases, covering the full flow.** 6 CausalT5k D3 cases (T1–T6): 2 each of YES, NO and AMBIGUOUS, at least one L3, the two NOs choosing different trap types, and none going into few-shot. 4 self-built, with inputs all taken from the four examples in the assignment: C1 enters only Event A "photonic chip adoption is faster than expected", finds candidates and picks one to form a proposal (Discovery + E1 + numeric E2, through the Semiconductor Pack); C2 enters A + Target B "models above Fable are export-restricted → the instrument the user gives", checks the path and forms a proposal (Inspect + document / event-type E2); C3 runs ChangeAssumption and AddShock separately on C1's graph (E3 + the proposal diff is traceable); C4 enters "the midterm elections split" against a distant instrument (E4 + Discovery abstention). Plus D1: the founder's own example from the call, "I think the Strait of Hormuz is going to open up next week", run through the whole flow with the Hormuz pack, only to show that it works across domains without inventing numbers. All cases go through the unified knowledge-base interface, and online search is on in only one case for demonstration, so that success or failure is not left to live search.

**Reporting rules.** One line per case: type, expectation, actual, pass or not, failure type. Report counts only, with no percentages; passing the two negative controls says something only about those two cases; no pass rate for ChatGPT is preset, and the comparison result comes from actual testing; CausalT5k was made public early this year, so the model may have seen it, and the 6 cases are a smoke test and not a score. No historical return backtest is done.

**The future L4.** Forecast calibration (Brier, calibration curves) and public forecasting benchmarks — [ForecastBench](https://forecastingresearch.substack.com/p/ai-llm-forecasting-model-forecastbench-benchmark), Metaculus's [FutureEval](https://metaculus.substack.com/p/metaculus-futureeval-ai-forecasting-benchmark), FutureSearch's [Bench to the Future](https://evals.futuresearch.ai/) — are deferred together with probability propagation. They measure whether a claim is accurate, not the consistency of invalidation conditions and forks that this POC cares about. The counterfactual tasks of BizFinBench.v2 are unconfirmed, so look at the task list before using it. As for the harness, [Inspect AI](https://inspect.aisi.org.uk) is the production path, and for three hours we use pytest + a human review sheet.

## Interface to the downstream

Up to the commit, this system outputs a **Conditional Trade Proposal, with status draft / needs_review**. Machine-readable does not mean executable: `portwatch.hormuz.daily_transits >= 20`, even if the schema is legal, does not prove that the series is really accessible, that the threshold 20 has a basis, that the update frequency and latency suit a trading decision, or that the contract and direction are settled. At most the validators guarantee the fields are complete. They cannot prove that the conditions for automatic execution are in place.

**Export (boundary only)**: JSON with a `proposal_version`; the Condition object carries kind, predicate, source or series, comparator, threshold (may be null), anchor, deadline, observation_window, rule, verification_status, evaluation_status. `approval_required` is always true. If the downstream wants to turn it into monitoring or a conditional order, it must first advance each Condition's verification_status to verifiable — this step is downstream and not in this system.

**Hooks**: deferred. No interface such as on_condition_fired is defined within three hours, and the README explains the future form in one sentence.

**Boundary**: position size, accounts, order routing and the translation of price stops are all downstream. This system makes only one commitment: a proposal can clearly answer "what else is needed to continue", instead of outputting a buy or sell direction every time.

## Runtime evolution (later, not done in three hours)

Evolvable, multi-user and swarm are runtime problems, not core problems. After the audit this whole section is demoted to "later": in three hours there is no plugin registry, no ledger platform, no four-command CLI. We only guarantee that the core code does not depend on any framework (schema, validators, diff, the two boundaries and the eval are ordinary Python modules), and the shell changes with the stage.

The three-stage runtime route (decided): the POC uses its own loop of about 50 lines (option A); the MVP stays "core library + web shell", and Claude Code (option B) is only a development tool and a conversational shell for internal testing, calling the core library's discover / inspect / fork / commit over MCP, with graph writes still going only through the validators — it is not allowed to be the loop, because its default is to let the model decide what to do, and the write scope inside it can only be asked of the model with a prompt; production uses a graph-orchestration framework (LangGraph and the like, option D) to run the core state machine, where its checkpoint corresponds to our snapshot and its approval interrupt corresponds to commit; a general agent framework (Hermes and the like, option C) runs only the slow loop — one monitoring agent per signed proposal, watching long-term until the expiry evaluation. What does not change across the three stages is the core library: schema, validators, snapshots, the two boundaries, the eval.

There is only one key constraint: the loop is a stateless function, but its input must explicitly carry state references — `run(op, graph_version, user_choice, config, user_id)` → new snapshot + operation-log entry. The old signature `run(belief, config, user_id)` cannot describe multi-turn operations: Fork must know the current graph version and which path the user chose, so even if the future is a stateless worker, the input must explicitly contain these references, so that the signature of a future architecture does not become a wrong constraint on the current MVP. Any worker can run any request, and adding machines does not change the code; user isolation is the user_id on snapshots and configuration (teams add a team_id); configuration is layered in three levels: system default \< organisation \< user, and the trusted-source whitelist is the first thing overridden per user. The table below is a reference for later stages and is not the MVP acceptance standard.

|                | Three-hour POC | Multi-user | swarm / teams |
|----------------|-------------------------------------------------------------------------------------------------------------------------|------------------------------------------------|---------------------------------------------------------------------------------------------------------|
| Where the loop runs | In process, the Claude SDK's Tool Runner | A queue + worker pool, the same function | A managed agent runtime, with sessions, permission policy and budget (candidate: Anthropic Managed Agents; to be compared side by side with a self-built worker pool at that time) |
| State | Version snapshots in memory + operation log (written out as JSON files is enough) | Postgres append-only tables + object storage for traces | Same as left + an event stream (webhook) |
| Scheduling (slow loop) | None (expiry evaluation is deferred as a whole) | cron scanning the ledger | Persistent timers (the expiry date spans several weeks, so a durable workflow or the scheduling built into a managed runtime is needed) |
| Interface | Vite + React + @xyflow/react for a read-only canvas + panel, one page with three tabs (as actually implemented; the Streamlit fallback was not used) | The same React Flow front end plus editing interaction, reading the same API | A shared thesis board + comments for several people |

Why in three hours we do not use a general agent framework such as Claude Code or Hermes as the runtime: our agent does not execute generated code, all four tools are read-only, and graph writes go only through the validators — a sandbox solves a problem we do not have; the default philosophy of a general framework is to let the model decide what to do, which is the opposite of "give it only the subtree, reject anything out of bounds", and this line can only be asked of the model with a prompt inside a framework, while in our own loop it is one `if`; and what the reviewers want to look at is exactly the loop itself. Claude Code is used to write this project, and not to be this project.

The three real uses of a swarm in this product, none of them multi-agent for its own sake: in the discovery stage, one sub-agent per direction builds chains in parallel (latency); review agents run independently with different models and different prompts (breaking self-agreement); one monitoring agent per committed spec (the slow loop). Writing the five roles with independent prompts each makes all three of these a runtime change and not a rewrite.

The three things to get right today so that they can be swapped later: the loop is a stateless function (state is in the version snapshots); the model enters only through the Reasoner, the single entry; the write scope is decided by the code and not by the prompt. They cost not one extra minute in the three hours.

## Key decision record

Rewritten after the audit. The README tells its trade-offs from this table; the three "deliberately deleted" items are where reviewers are most likely to push, and you must be able to say in one sentence why.

| Decision | Alternative | Why | Cost |
|------------------------------------------------------------------|------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------|
| The graph is a stateful structured object, with version snapshots | Regenerate an article every time; a full event-sourcing ledger | The basis for audit, fork and UI diff; three hours need only the chain v1 → operation → v2 → diff | Calling the model again cannot be guaranteed to give the same result, so the snapshot stores the model output and the tool observations |
| The model proposes, the code decides structure only | The model regenerates the whole graph; judge causal correctness with a schema | Validators can guarantee fields and scope, but cannot guarantee that the financial causation holds; causal correctness relies on evidence status and human review | A person has to look at a small sample |
| Claim and Condition are separate, and Condition uses three time predicates | A numeric four-tuple per node | Not every node corresponds to a numeric series; "deadline passed with nothing happening" is a legal condition; forcing a four-tuple pushes the model to invent indicators | The evaluation method is chosen by type, which is one more branch to implement |
| Deliberately delete probability propagation | noisy-OR / Bayesian propagation as a plugin | The product of three model-estimated probabilities is not the probability that a trade succeeds; conditional dependence, common causes and market expectations are all unmodelled; a wrong abstraction costs more than none | A fork answers only "which paths are challenged" and gives no number |
| Deliberately delete the unsourced disagreement score | p_user − p_model as trading edge | A model probability is not the market consensus, and the difference between the two says only that the judgments differ; if there is market data, show it and state what question it answers | Ranking becomes research priority and not an alpha ranking |
| Discover gives at most 3, or abstains | At least 3 every time, at least 1 counter-intuitive | A hard count rewards fabrication and contradicts "dare to say no" | Sometimes there is only one direction on screen, or none |
| Scenario, observation and invalidation are three separate states | A scenario directly triggers invalidation, take-profit turns into stop-loss | Supposing Iran is struck does not mean shipping has stopped, still less does it imply a stop price; visual drama cannot manufacture a financial conclusion | The fork's wow becomes "challenged + what to check next" |
| A proposal is a draft, and machine-readable does not mean executable | The spec can be polled and executed directly | Whether the series exists, whether the threshold has a basis, whether the latency is acceptable are not things a schema can prove | The downstream interface defines only the boundary |
| Keep only the two boundaries Reasoner and Evidence Provider | Six plugins + two propagators | The rest have unsettled semantics, and abstracting early would harden mistakes | The proof of extensibility is carried instead by "swap the model and run the same eval" |
| Write our own loop, and do not use a general agent framework | Claude Code headless + harness; Hermes | The tools are read-only and execute no code, so a sandbox has no use; write-scope control in a framework can only be done with a prompt | Maintaining a loop of about 50 lines |
| Evidence before reasoning, with citations the code can validate | Build the graph first, then find evidence to hang on the edges | Making up the story first and then fitting citations degrades into citation laundering; the evidence pack goes into the context first, and excerpt_id is validated by the Reference Validator | In three hours only pre-reviewed evidence packs are supported, with no live retrieval |
| The write scope is decided by the code before the graph is changed | The same model output declares its own scope | The model cannot authorise itself; AddShock's Stage 1 only proposes attachment points, and the code fixes the scope from them before letting the model change anything | In three hours predefined demo shock attachment points are used, and arbitrary shocks are left for later |
| Entry conditions default to AND, and the empty set does not pass | Any one met lifts WAIT | Necessary conditions must all be met; missing and unknown do not count as met; even when all are met it only reaches Ready for Review | One more truth-table unit test |
| max_visible_hops replaces max_hops; three logical stages called on demand replace a fixed three calls | A hard back-end limit of ≤3 hops; promising three model calls | Three steps is a UX simplification and not a reasoning limit: forcing six steps into three drops key premises (such as the airline having hedged fuel); the number of calls is affected by retrieval and retries, so the document should constrain each stage's input, output and cost cap | The display layer must fold the trunk and list extra dependencies in the details (no arbitrary expansion in three hours); the eval changes from "no more than three steps" to "causal completeness and key dependency" |
| Three-stage runtime route: A → core library + shell (B only as a shell) → D runs the core, C runs the slow loop | B directly as the MVP runtime; C / D, either one, running everything | Claude Code's default is to let the model decide what to do, and the write scope can only be asked of the model with a prompt; D's checkpoint and approval interrupt line up with snapshots and commit; C is good at long-term watching and not at an auditable core loop | The MVP stage has one more MCP wrapper layer; in production the 50-line loop is moved into a graph |
| A unified knowledge-base interface, with packs split by industry | One data source covering all industries; or connecting OpenSearch / a vector store directly | TrendForce understands only semiconductors, and other industries each have more authoritative sources; a few dozen excerpts need only BM25, and a vector store is for when the scale reaches thousands | Each industry added needs one pack organised by hand |
| The local knowledge base goes into the context whole, with no retrieval | BM25 / RAG retrieval | The two packs are about 16k tokens, and one Inspect on Haiku costs about $0.005; the quality of C1 and D1 with the whole pack has been verified; retrieval instead risks missing a key excerpt | When the packs grow we must switch to RAG (next phase) |
| Retrieval goes to the agent, and the stance judgment is taken away from the model that draws the conclusion | No tools at all during reasoning; or let the model search while it reasons and judge stance itself | Checking a claim is an open-ended task and the path cannot be fixed; the risk of drawing the conclusion first and then finding citations is guarded by three mechanisms: stance is labelled by a step that cannot see the conclusion, every round must look for the other side, and citations can point only to original text the tools really returned | The number of calls and the spend rise; re-recording the same case changes the result, and the eval has to look at stability |
| Research and graph building are separate (option A), and the "submit graph" tool goes to the next phase | Put a submit_graph tool in the loop, or build the graph bit by bit with tools | The code for graph building and plan generation need not change; retrieval with citations and strict JSON cannot go in the same call | Graph building cannot see validation feedback immediately inside the loop (retries are the backstop) |
| One graph with several competing branches + one plan per conclusion + approve one | A single path + sign-off | The decision depends on "which premise you believe"; the divergence point is the key dependency; the same signal is an entry on one branch and often an exit on another | The number of plans grows with the branches; the approval semantics and invalidation rules must be written as code |
| Add neutral to the evidence stance | Only supports / contradicts | Background information such as methodology notes and update frequency would be forced to pick one of two, creating false support or a false opposing side | The evidence packs have to be relabelled |

## Risks and mitigations

| Risk | Consequence | Mitigation | How we know it happened |
|---------------------------------------------------------|------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------|-------------------------------------------|
| The model writes nodes outside the scope during a fork | The user cannot tell change from noise | The write scope is computed by the code; out-of-bounds writes are discarded | E3 automatic test |
| The model invents a data series or threshold to satisfy the schema | The proposal looks executable but is made up | Claim and Condition are separate; unverified is allowed; the source type is chosen by Claim type | E1 by hand: can each series and threshold point to a basis |
| Refusing when it should build the chain (Skepticism Trap), or following the user's assertion and saying YES | Discovery is either empty or sycophantic | Discover allows 0–3; CausalT5k's YES and sycophancy-trap cases go into the eval | E4 |
| A scenario is treated as an observation, and a premise is directly marked invalid | Manufactures a firm financial conclusion | Four kinds of Claim state; a scenario only produces "challenged" | E3 + a person reads the diff wording |
| An invalidation condition is empty talk with no way to judge it | The product degrades into a prompt | A Condition must carry a rule; the forbidden-phrasing list forbids only vague statements | E2 |
| The evidence source is trustworthy but does not support this causation | A chain that looks grounded | Each piece of evidence states which part it supports | E1 |
| Three hours grow back into a dozen projects | Only architecture and no experience | Follow the time allocation table: the first real model output must be seen within the first 30 minutes; the UI has a hard cutoff from minute 115, and the eval and README from minute 150; on overrun, deliver one complete, usable Seed Case, and do not deliver five half-finished interfaces | The schedule |
| During AddShock the model quietly changes dependency edges while the node text stays the same | The causal model has changed but the hash comparison cannot see it | The write scope includes edges; two-stage AddShock; E3 compares nodes and edges and traces changes | E3 automatic test |
| not_observed_by is judged "did not happen" when the data source has not been updated | A wrong exit trigger | evaluation_status has three values (met / not_met / unknown); not_observed_by gives met only when the observation_window has ended, the source covers that window and nothing was observed in the window, otherwise unknown | E2 human review + unit tests |
| The model makes up a causal story first and then finds material to fit it (citation laundering) | The graph has citations, but the citations do not support the causal conclusion | Evidence before reasoning: the evidence pack goes into the context first, edges cite excerpt_id, and the Reference Validator checks that the citation exists in the evidence pack | E1 by hand: does the quoted original text support the mechanism |
| Entry conditions judged as "any one met" | One met lifts WAIT while another is not yet verified | AND by default; unknown → WAIT, not_met → BLOCKED, the empty set does not pass; even when all are met it only reaches Ready for Review | Truth-table unit test |
| One path being challenged makes the whole argument judged invalid | Ignores the other paths that still hold, and manufactures a false invalidation | The ClaimGraph is a DAG; the Scenario Assessment is recorded per claim; a key dependency failing does not automatically invalidate the argument | E3 Expected Impact + a person reads the diff wording |

## Mapping to the three hours

Every component in the architecture has a status: build, stub, or not building. Stub means the interface exists and the default implementation is the thinnest, and the README says so.

| Priority | Component | Delivery standard |
|--------|------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 1 | Typed Graph + Condition | The three kinds of state — assumption, evidence, condition evaluation — are kept separate and do not share a field; a threshold may be null; Condition carries anchor / deadline / observation_window; verifiable ≠ met is written as code |
| 2 | Structured Reasoner | Discover (0–3 or abstain, with the three kinds of label) or Inspect can generate constrained candidates; the three logical stages are called on demand, each stage with a cost cap; no hard limit on path depth, with 3 main stages shown by default |
| 3 | Evidence Grounding | Evidence before reasoning: the knowledge base (Semiconductor Pack + Hormuz pack, unified interface, packs added by industry later) goes into the context first, edges cite excerpt_id, and the Reference Validator checks that the citation exists; state the stance and which part it concerns, and the evidence pack contains opposing material; edges with evidence and model_only edges are clearly distinguished; no invented thresholds |
| 4 | Fork + Scoped Patch | The write scope is fixed by the code first; ChangeAssumption and a limited AddShock (predefined attachment points); unaffected nodes and edges stay as they were; "challenged" is written into the Scenario Assessment; the baseline version is kept |
| 5 | Conditional Trade Proposal | Consistent with the graph version; derived analysis and user judgment are separate; the entry-condition AND truth table (WAIT / BLOCKED / Ready for Review) is written as unit tests; zero candidates produce no proposal |
| 6 | Focused Eval | 10 cases (T1–T6 + C1–C4) with per-case results and failure types; E3 Non-interference automatic + Expected Impact with golden cases; CausalT5k outputs only the causal judgment and no proposal |
| — | Market reference, Critic, UI animation | Optional; given up in that order when time runs short |
| — | Six plugin interfaces, two propagators, noisy-OR, Brier calibration, JSONL ledger, schema migration, four-command CLI, hooks, multi-user, swarm, continuous monitoring, canvas, historical replay | Deferred or deleted; README "next steps" and "deliberately not built" |

Order and time allocation (after the final audit): "do not write a prompt in the first 30 minutes" is no longer a hard rule. The biggest unknown in this project is not whether a schema can be written, but whether, given limited evidence, the model can generate meaningful causal conditions; if the first real model output is seen only in the middle or late stage, there is no time to fix the most important reasoning problem. The experience that must be completed: enter an event and get reasonable candidates or an explicit abstention; pick a direction and see a short causal chain with the key dependency; change one assumption and see the correct local change; get a proposal that distinguishes the known, the unknown and what awaits review.

| Time | Goal |
|--------------|------------------------------------------------------------------------------------------------------|
| 0–30 minutes | A minimal schema + validators, and run one Inspect sample right away (the first real model output must appear here) |
| 30–75 minutes | Discover / Inspect and the Evidence Pack (evidence before reasoning, citation validation) |
| 75–115 minutes | ChangeAssumption, a limited AddShock (predefined attachment points), Patch / Diff, Scenario Assessment |
| 115–150 minutes | Front end: a read-only React Flow canvas + panel + sign-off table (later changed to approve a plan) + three-state diff, running the full user path; if it does not work by the deadline, switch to the Streamlit fallback (not actually used) |
| 150–180 minutes | Run the core eval, record failures, finish the README |

The premise is that a usable project scaffold and model-calling environment already exist. The trade-off on overrun: it is better to deliver one complete, usable Seed Case with clearly reported test results than a system in which all five interfaces exist but not one user path is complete and usable. When time runs short, lower in this order: ranking refinement → Critic → market reference → UI animation; do not sacrifice state consistency, evidence labelling, the refusal mechanism or the end-to-end flow first. The README needs a paragraph on "what we deliberately do not build, and why".

## Acceptance checklist: the 7 items the engineering review will look at

- Given Event A, it can discover candidates or reasonably abstain

- After a candidate is chosen, it can explain a causal mechanism of at most three hops

- Key conditions do not make up sources, thresholds or decision dates

- After an assumption is changed, the relevant paths update correctly and the unrelated parts stay unchanged

- When conditions are not yet met or not verified, the proposal stays WAIT / needs_review

- The user can view a clear research proposal and its evidence status

- The eval can output per-case results, including the reasons for failure

These seven items are the POC's completion standard, and matter more than "all five interfaces exist".
